# VENU — план разработки

> Ревизия от 26 августа 2026. Версии стека и рабочий контракт — в [CLAUDE.md](CLAUDE.md).

## Питч

**VENU** — мультитенантная платформа продажи билетов на события. Независимые
организаторы публикуют события и продают билеты по тарифам из своего дашборда;
посетители просматривают серверно-рендеренную ленту событий и оформляют покупку
через Stripe. Система построена вокруг одной сложной задачи — **никогда не продать
одно и то же место дважды** — и доказывает это **прямо в браузере**: клик
«Забронировать» на последнем месте, UI мгновенно показывает «забронировано», затем
откатывается назад, если атомарная проверка на бэкенде говорит, что кто-то успел
раньше. Это демо-момент для README (записать GIF).

## Цель и калибровка

Проект под вакансию **Frontend Developer**. Предыдущий пет-проект (BITO,
мультитенантный POS) уже «продал» в резюме историю про MongoDB-транзакции,
no-oversell и идемпотентные вебхуки. VENU не должен быть второй версией того же
рассказа, но и вырезать атомарную защиту от overselling нельзя: без неё продукт
физически багованный (продаст одно место дважды) — это условие корректности, а не
витрина. **Решение: бэкенд не режем, а время, сэкономленное на переиспользовании
знакомых паттернов, адресно вкладываем во фронтенд** (см. «Перевес во фронтенд»).

### Что действительно ново для автора

| Ново | Почему сложно |
|---|---|
| **Next.js как фреймворк** | Опыт — только создание файлов в `pages/`. Ни одной фичи: ни RSC, ни кэша, ни ревалидации, ни метаданных, ни `next/image`. Это главный обучающий блок |
| **Optimistic updates** | `onMutate` / context / откат — явно заявленный пробел |
| **Автотесты** | Нулевой опыт. При 3+ годах стажа это самый заметный пробел в резюме |
| **Загрузка файлов** | multipart, хранилище, граница доверия |
| **Реальный Stripe** | Живые вебхуки, CLI forwarding, «редирект ≠ оплата» |
| **Компоненты с нуля** | Tailwind знаком по работе, но Dialog/Select/Toast с focus-trap и ARIA руками — не делал |
| **Осознанный a11y и Core Web Vitals** | Ни то, ни другое не делалось намеренно и не измерялось |
| **Компенсирующие действия** | Безопасно отменить декремент инвентаря |

### Что переносится из BITO как знакомая почва

`HttpError`/`asyncHandler`/`errorHandler` · JWT access в памяти + refresh в
httpOnly-куке + retry на 401 · `requireAuth`/`requireRole` · скоупинг по `tenantId`
в сервисном слое · `session.withTransaction` + условный `findOneAndUpdate` ·
`express.raw()` до `express.json()` · коллекция `WebhookEvent` с уникальным
индексом · агрегации для отчётов · составные индексы и `.populate()` против N+1 ·
Docker Compose с Mongo `rs0` · TanStack Query, Zustand, FSD-подобная слоистость.

Tailwind, TypeScript, React 19, TanStack Query, Zustand, роутинг, ESLint flat
config — тоже знакомая почва (рабочий стек), не обучающие этапы.

## Модель данных

- **Tenant (организатор):** `name`, `slug` (уникальный — публичные URL
  организатор-скоупные, `/o/<slug>/...`), `currency`, `logoUrl?`.
- **User (только сотрудники организатора, НЕ покупатели):** `tenantId`, `email`,
  `passwordHash` (`select:false`), `role: "owner" | "staff"`.
  Индекс `{tenantId:1, email:1}` уникальный.
- **Event:** `tenantId`, `title`, `slug`, `description`, `venue`, `startsAt`,
  `endsAt`, `status: draft|published|cancelled`, `coverImage`, `createdBy`.
  - `{tenantId:1, startsAt:-1}` — список в дашборде.
  - `{tenantId:1, slug:1}` уникальный — публичный URL внутри организатора.
  - `{status:1, startsAt:1}` — **единственное осознанное исключение из правила
    «tenantId первым»**: публичная лента запрашивает опубликованные события across
    всех тенантов. Обосновать в документе решений, а не оставлять выглядеть ошибкой.
- **TicketType (тариф):** `tenantId`, `eventId`, `name`, `priceCents` (целые центы),
  `quantityTotal`, `quantityAvailable`, `quantitySold`, `maxPerOrder`, `salesEndAt`.
  - `quantityAvailable` — наследник `product.stock` из BITO. Три счётчика, а не один,
    потому что появилось промежуточное состояние, которого в BITO не было:
    «забронировано, но не оплачено».
- **Order (бронь → оплата → билеты; одна коллекция, один state machine):**
  `tenantId`, `eventId`, `orderCode` (неугадываемый, публичный), `buyerSessionId`
  (анонимный), `buyerEmail`, `items[]` (снапшот имени и цены — как снапшот
  `costPrice` в BITO), `totalCents`,
  `status: held|pending_payment|paid|expired|cancelled`, `expiresAt`,
  `stripeCheckoutSessionId`.
  - `{tenantId:1, createdAt:-1}`, `{status:1, expiresAt:1}` (запрос «подметальщика»:
    равенство перед диапазоном), `{stripeCheckoutSessionId:1}` уникальный+sparse,
    `{orderCode:1}` уникальный.
- **Ticket:** `tenantId`, `eventId`, `orderId`, `ticketTypeId`, `code` (уникальный),
  `checkedInAt`. Создаётся внутри транзакции подтверждения оплаты, N документов на N мест.
- **WebhookEvent:** `eventId` (настоящий `evt_...` от Stripe), `type`, `receivedAt`.
  Уникальный индекс на `eventId`.

**Мысль для документа решений:** один приём — **условный `findOneAndUpdate`, где
фильтр И ЕСТЬ проверка** — решает три разные задачи: no-oversell
(`quantityAvailable: {$gte: qty}`), вебхук ровно один раз (фильтр по
`status: "pending_payment"`), возврат брони ровно один раз (фильтр по
`status: "held"`). Самая «продаваемая» на собеседовании идея проекта.

## Перевес во фронтенд

Четыре пункта, которые пронизывают все этапы, а не ждут финала. Именно сюда идёт
время, сэкономленное на переиспользовании бэкенд-паттернов.

1. **Skeleton-состояния и микроанимации.** Каждый список и каждая карточка имеют
   skeleton, а не спиннер. Переходы состояний (появление, откат брони, смена
   статуса) анимированы. Правило: `prefers-reduced-motion` уважается везде.
   Вводится на Этапе 1 как часть дизайн-системы, применяется в каждом следующем этапе.
2. **Осознанный a11y-проход.** Не только Dialog/Select/Toast: keyboard-навигация по
   всем интерактивным элементам, видимый focus-ring, ARIA на самописных
   компонентах, корректные роли и `aria-live` для откатов и тостов, семантические
   заголовки, контраст. Проверка axe + прогон табом без мыши — в чек-листе каждого
   этапа с UI.
3. **Lighthouse / Core Web Vitals.** Замер после Этапов 5, 6 и 11. `next/image` с
   правильными `sizes`, шрифты через `next/font`, анализ бандла, `Suspense` +
   streaming там, где это реально помогает LCP. Цифры до/после — в README.
4. **Перевес тестов в сторону фронтенда.** На бэкенде остаётся звёздный
   oversell-тест и минимально необходимое вокруг него; основной объём — RTL-тесты
   на откат optimistic update, валидацию форм, состояния загрузки/пустоты/ошибки,
   доступность компонентов. Подробнее — Этап 10.

## Этапы

Размеры: **S** ≈ один присест, **M** ≈ пара сессий, **L** ≈ несколько сессий.

### Этап 0 — Инфраструктурный каркас (M) `[знакомо]`

Compose с Mongo `rs0`, скелет Express (`env`/`db`/`HttpError`/`asyncHandler`/
`errorHandler`/health-роут), Next-приложение (App Router, TS, Tailwind), `/api`
rewrite к бэкенду, seed-скрипт, структура папок.

- **`/api` rewrite критически важен.** В BITO прокси Vite давал браузеру один
  origin, и httpOnly refresh-кука просто работала. Rewrite Next'а должен
  воспроизвести это же — иначе первый день уйдёт на отладку CORS и origin кук.
- Tailwind закреплён на **v4** (CSS-first конфиг через `@theme`, без
  `tailwind.config.js`).
- Next 16: `params`/`searchParams` — **промисы**, их надо await'ить.
- Модули: ESM + `nodenext` → в относительных импортах писать `.js`, даже если файл `.ts`.

### Этап 1 — Дизайн-система и каркас приложения (M) `[частично ново]`

Корневой layout, навигация, route groups (публика vs дашборд), примитивы
Button/Input/Label/Card/Badge/Spinner/EmptyState/**Skeleton**, шкала отступов и
типографики, адаптивные брейкпоинты, `prefers-reduced-motion`. **Делать до фич, а
не приклеивать в конце** — именно так BITO остался голым.

- Tailwind знаком, поэтому этап не про синтаксис, а про **систему**: токены темы в
  `@theme`, единая шкала, вариативность компонентов, хелпер `cn()` на
  `clsx` + `tailwind-merge` (объяснить, зачем именно `-merge`, а не просто `clsx`).
- Skeleton — примитив первого класса, наравне с Button. Не «добавим потом».
- Route groups App Router'а — первое настоящее знакомство с файловым роутингом
  Next'а (не с роутингом вообще).
- Focus-ring и порядок табуляции задаются здесь, на уровне примитивов, — тогда
  a11y не придётся «прикручивать» на 11 этапе.

### Этап 2 — Аутентификация организатора (M) `[знакомо — этап уверенности]`

Логин, `/me`, refresh, logout, защищённый layout дашборда, Zustand-стор токена,
обёртка `apiFetch`. ~90% прямой перенос из BITO. **Рефреш-токены попадают сюда, а не
откладываются в конец, как в прошлый раз** — видимый прогресс.

- `'use client'` и граница токена: Zustand живёт в памяти браузера, Server Component
  её не видит. Дашборд — client-поддерево, публичные страницы — серверные.
  Проговорить до написания кода.
- **НЕ защищать роуты в `middleware.ts`** — Next middleware видит только куки, а
  access-токен намеренно не в куке. Защита на клиенте — только UX; **единственный
  реальный авторитет — API**, там fail-closed. Это архитектурное решение, в документ.
- TanStack Query требует `'use client'` Providers-компонента с `QueryClient`,
  созданным внутри `useState`, а не на уровне модуля — иначе течёт между запросами
  на сервере.
- Роли переименованы: `admin→owner`, `cashier→staff` — повод передумать логику
  заново, а не слепо копировать.

### Этап 3 — Организатор создаёт события (M) `[знакомо]`

Модель Event + сервис со скоупингом по тенанту + CRUD, список в дашборде, формы
создания и редактирования, переключатель draft/published.

- Первая многополевая форма: дата/время и таймзоны — хранить UTC, показывать
  локальное, выбрать одну конвенцию и держаться её.
- **`404`, а не `403`** для события чужого тенанта (в BITO был 403, который выдаёт
  сам факт существования ресурса). Станет тестом на Этапе 10.
- Генерация slug + уникальность в рамках тенанта (ошибка дубликата ключа → аккуратный
  `HttpError`).
- Фронтовая часть: состояния загрузки/пустоты/ошибки формы, `aria-invalid` и
  `aria-describedby` на полях, ошибки в `aria-live`. Это первое место, где
  a11y-проход становится привычкой.

### Этап 4 — Загрузка обложки события (M) `[НОВОЕ: multipart, граница доверия]`

Роут загрузки на multer, валидация, хранилище за абстракцией
`storage.save(file) → {url}`, отображение в дашборде и на публичной странице.

- **multer → локальный диск на Docker volume**, не S3/Cloudinary: ноль внешних
  аккаунтов, урок остаётся про multipart и границу доверия. Ограничение признать
  прямо: не переживёт пересборку контейнера, не масштабируется горизонтально.
- **`apiFetch` из BITO жёстко прописывает `Content-Type: application/json`** — это
  **сломается** на загрузке файла (ключ заголовка не убрать простым спредом; вручную
  выставленный `multipart/form-data` без boundary ломает multer). Решение: ставить
  JSON-заголовок только если тело — не `FormData`. Полноценное упражнение на отладку.
- Граница доверия: никогда не доверять имени файла от клиента (path traversal) или
  заявленному mime-типу — имя генерировать на сервере, ограничивать размер,
  проверять реальный тип. Эхо правила BITO «клиент никогда не задаёт цену».
- `next/image` требует `remotePatterns` для хоста загрузки.
- Фронт: превью до отправки, индикатор прогресса, drag-and-drop с доступной
  клавиатурной альтернативой, понятная ошибка при превышении размера.

### Этап 5 — Тарифы + публичная лента событий (SSR) (L) `[НОВОЕ: RSC, SSR, кэш]`

CRUD тарифов (сторона организатора), публичная серверно-рендеренная лента с
фильтрами, публичная страница события с живой доступностью мест, публичная страница
организатора.

- **Этап, где Next.js окупается, и главный обучающий блок проекта.** Публичные
  страницы — Server Components, запрашивающие данные на момент запроса (настоящий
  HTML в view-source, `generateMetadata` на каждое событие для превью-карточек в
  соцсетях).
- **На сервере не существует относительных URL** (`fetch('/api/events')` работает в
  браузере и падает в Server Component) — нужен серверный хелпер с абсолютным
  базовым URL, отдельный от браузерного `apiFetch`. Главная стена App Router'а.
- Кэширование: доступность билетов не должна кэшироваться устаревшей — явно
  исключить страницу события из кэша и уметь объяснить, почему.
- Кросс-тенантный запрос ленты — первый не-tenant-скоупленный запрос, нуждается в
  собственном обосновании и собственном индексе.
- N+1 снова: ленте нужна самая дешёвая цена тарифа для каждого события. В лоб = 1+N.
  Чинится агрегацией с `$lookup` или батч-запросом.
- **Первый замер Lighthouse.** `next/image` с корректными `sizes`, `next/font`,
  `Suspense` + streaming для ленты. Зафиксировать цифры до/после.

### Этап 6 — Бронирование: атомарная защита + optimistic UI (L) ⭐ центральный

`POST` на бронь → транзакция, условный декремент `quantityAvailable` по каждой
позиции, `Order` со статусом `held` и `expiresAt` (~10 мин), `409` при неудаче.
Фронт: кнопка брони с optimistic-декрементом, таймер брони, откат и объяснение при
`409`. **Не торопиться.**

- `createOrder` из BITO — почти точный шаблон бэкенд-части.
- **Optimistic updates — заявленный пробел.** Разобрать контракт из четырёх
  колбэков до кода: `onMutate` (отменить летящие рефетчи, снять снимок кэша,
  записать optimistic-значение, **вернуть** снимок как context) → `onError(err,
  vars, context)` (восстановить из context) → `onSettled` (инвалидировать, чтобы
  сервер снова стал источником правды). Шаг «верни context» — самое неочевидное.
- **Путь неудачи И ЕСТЬ фича** — два браузера, одно место, оба кликают; один
  побеждает, другой заметно откатывается с объяснением. Это демо-GIF, заменяющий
  curl-стресс-тест BITO на визуально понятное.
- Откат должен быть **заметным и доступным**: анимация возврата счётчика,
  объяснение в `aria-live`, фокус не теряется.
- Анонимная личность покупателя через `buyerSessionId` (UUID в localStorage или
  кука) — без аккаунтов покупателей.
- Таймер обратного отсчёта + SSR = **hydration mismatch** (сервер рендерит другое
  «осталось времени», чем первый рендер клиента). Предупредить заранее: выглядит как
  страшная React-ошибка по банальной причине.
- Сервер пересчитывает цену и сумму из базы; клиент присылает только
  `{ticketTypeId, quantity}`. Также проверять `maxPerOrder` на сервере.
- **Второй замер Lighthouse** на публичной странице события.

### Этап 7 — Истечение брони: возврат инвентаря (M) `[НОВОЕ: компенсации]`

«Подметальщик» по интервалу: находит `{status:"held", expiresAt:{$lt:now}}`, по
каждому заказу в транзакции условно переключает `held→expired` и `$inc` возвращает
`quantityAvailable` каждого тарифа вверх.

- Декремент был лёгким; безопасно его **отменить** — сложная половина.
- **Не использовать TTL-индекс Mongo** — он удаляет документ (уничтожает историю
  аудита и никогда не возвращает инвентарь). Заманчиво и неверно — обдумать и
  отвергнуть письменно.
- **Двойной возврат — вот в чём опасность.** Если «подметальщик» запустится дважды,
  наивный код вернёт инвентарь дважды (overselling в обратную сторону). Решение —
  тот же условный-update приём. Третье появление паттерна, назвать явно.
- **`pending_payment` никогда не «подметается»** — покупатель сидит на странице
  Stripe; истечение брони посреди оплаты = взять деньги за освобождённое место.
  Лучший edge-кейс проекта.
- Однопроцессный `setInterval` — честное решение здесь; отметить, что несколько
  реплик потребовали бы распределённой блокировки или очереди задач.

### Этап 8 — Stripe Checkout + идемпотентность вебхука (L) `[паттерн знаком, провайдер нов]`

Создание Checkout Session на сервере (позиции с ценой из базы,
`metadata{orderId,tenantId}`), `held→pending_payment`, редирект; обработчик вебхука
с проверкой реальных подписей; на `checkout.session.completed` — транзакционный
переход в `paid`, `$inc quantitySold`, выпуск N документов `Ticket`; страница чека
покупателя по `orderCode`.

- **`express.raw()` до `express.json()`, только для роута вебхука** — тот же паттерн,
  что в BITO, теперь с реальной причиной.
- **Checkout Sessions, а не Payment Intents + Elements** — хостед-страница означает
  отсутствие формы карты, клиентских секретов и обработки 3DS, тривиальный PCI-скоуп.
  К уроку про идемпотентность Elements ничего не добавляет.
- Проверка подписи переходит на `stripe.webhooks.constructEvent` — узнать в ней тот
  же HMAC над сырым телом, что писали руками в BITO.
- **Редирект успеха — НЕ доказательство оплаты.** На этот URL может перейти кто
  угодно вручную. Только вебхук переводит в `paid`. Возможно, самая важная строчка
  проекта.
- Реальные вебхуки приходят как минимум один раз, могут дублироваться и приходить не
  по порядку (Stripe ретраит несколько дней) — проверить уникальный индекс на
  `eventId` против `checkout.session.completed`, `.expired`,
  `payment_intent.payment_failed`.
- `stripe listen --forward-to` для локальной доставки — **секрет подписи у CLI
  отличается от секрета в дашборде**, их смешение выглядит как баг в коде.
- Неудачный или истёкший checkout должен возвращать инвентарь — переиспользовать
  путь возврата из Этапа 7, не писать второй.

### Этап 9 — Дашборд организатора + отчёт по продажам (M) `[знакомо]`

Агрегация с ролевым доступом: выручка и проданные билеты по событию и тарифу, список
посетителей, процент распроданности.

- Замена «скрыть маржу от кассира»: `owner` видит валовую выручку, комиссии и
  **email покупателей**; `staff` — только количество билетов и статус check-in.
- Применять через проекцию на уровне запроса (как `.select("-costPrice")`), а не
  условный JSX — сырой токен `staff` не должен получить email покупателей через API.
- Новая форма агрегации: `$lookup` для джойна с событиями, опционально `$facet` для
  итогов и разбивки за один запрос.
- Фронт: это место для настоящей витрины — таблицы с сортировкой, доступные
  графики (с текстовой альтернативой), skeleton'ы, пустые состояния.

### Этап 10 — Тесты (M) `[НОВОЕ: всё целиком]`

Vitest на обеих сторонах. **Баланс сознательно смещён во фронтенд**: бэкенд-паттерны
уже проверены в BITO, а RTL-тестов у автора нет вообще.

**Бэкенд — Vitest + supertest против настоящего Mongo с replica set:**
1. ⭐ **Overselling:** 5 мест, 20 одновременных броней через `Promise.all` → ровно 5
   успешны, 15 получают 409, `quantityAvailable === 0`. Главный тест проекта.
2. **Откат при частичной неудаче:** два тарифа, второй распродан → вся транзакция
   откатывается, первый тариф не тронут.
3. **Идемпотентность вебхука:** один `evt_` дважды → оплачен один раз,
   `quantitySold` увеличен один раз, ровно N билетов.
4. **Двойной возврат:** «подметальщик» дважды на одной истёкшей брони → инвентарь
   восстановлен ровно один раз.
5. **Изоляция тенантов:** токен организации A против события организации B → 404.

**Фронтенд — Vitest + React Testing Library (основной объём):**
1. **Откат optimistic update:** мутация отклоняется 409 → счётчик доступности
   возвращается к прежнему значению, показано объяснение.
2. **Успешный optimistic update:** счётчик уменьшается до ответа сервера,
   инвалидация приводит кэш к серверной правде.
3. **Валидация формы события:** обязательные поля, `aria-invalid`, ошибка
   объявляется через `aria-live`.
4. **Состояния списка:** skeleton → данные, skeleton → пусто, skeleton → ошибка с
   повтором.
5. **Доступность Dialog:** открытие ставит фокус внутрь, Escape закрывает, Tab не
   уходит за пределы, закрытие возвращает фокус на триггер.
6. **Доступность Select:** управление стрелками, Home/End, выбор Enter, корректные
   `aria-activedescendant` и роли.
7. **`prefers-reduced-motion`:** анимации отключаются при включённой настройке.

- **Транзакциям нужен replica set** — обычный `MongoMemoryServer` упадёт с
  непонятной ошибкой. Использовать `MongoMemoryReplSet` или отдельную тестовую базу
  в compose. Предупредить до первого тестового файла.
- Вне рамок: Playwright, пороги покрытия, тесты тривиальных хелперов. Двенадцать
  значимых тестов лучше ста двадцати поверхностных.

## Документ решений (9 разделов)

1. Как tenant и role идут от токена до слоя данных — и единственное осознанное
   исключение (запрос публичной ленты).
2. Архитектура Next.js: почему отдельный Express API, где граница Server/Client,
   почему access-токен никогда её не пересекает, почему защита роутов — клиентский
   UX, а единственный реальный авторитет — API.
3. Форма запросов и дизайн индексов — каждый индекс, порядок полей, почему
   (включая N+1 у ленты и единственный индекс без `tenantId` первым).
4. Почему покупатели — не users: гостевой чекаут, анонимные брони по сессии,
   неугадываемые коды заказов, и чего это стоит.
5. Граница доверия к клиенту — доверяем (id тарифа + количество), пересчитываем
   (цена, суммы, доступность), никогда не доверяем (редирект успеха как
   доказательство оплаты; имя и mime-тип загруженного файла).
6. Гарантия отсутствия overselling под конкурентностью — атомарный условный
   декремент, почему держится, где ломается.
7. Возврат забронированного инвентаря как компенсирующее действие — почему не TTL,
   почему двойной возврат опасен, почему `pending_payment` никогда не «подметается».
8. Идемпотентность, повтор и не-по-порядку доставка вебхуков Stripe.
9. Что было приоритезировано под давлением времени, что срезано, и с чем я бы
   поспорил.

## Решение: UI-кит — всё руками

Все компоненты пишем сами, включая Dialog/Select/Toast с focus-trap, обработкой
Escape и клика вне области, ARIA и порталами. shadcn/ui не используем.

Причина не «чужой код опасен», а прямая: **автор хочет практики именно здесь.**
Tailwind знаком по работе, а вот доступные оверлеи и составные компоненты руками не
делались ни разу — это ровно тот навык, который отличает фронтендера, умеющего
верстать, от фронтендера, умеющего проектировать интерфейс. Плюс это делает
a11y-проход (см. «Перевес во фронтенд») содержательным, а не декоративным: если
Dialog свой, то и focus-trap свой, и тест на него свой.

Формулировка для собеседования: *«Дизайн-систему и доступные оверлеи написал сам —
focus-trap, возврат фокуса, роли и aria-активный элемент, с тестами на клавиатурную
навигацию».*

## Решение: real-time — отложить в stretch, polling как честный MVP

В MVP — polling через `refetchInterval`. SSE — Этап 12.

- Optimistic-откат на Этапе 6 уже даёт наглядное доказательство конкурентности;
  real-time пересказал бы ту же историю за высокую цену.
- Это сквозная функциональность (доступность меняется при брони, при подтверждении
  вебхуком И при истечении у «подметальщика») — прикручивать её посреди разработки
  значит тащить «и ещё нужно эмитить событие» через каждый следующий этап.
- Новый инфраструктурный риск: реестр соединений, каналы, переподключение и —
  конкретно — буферизация SSE через rewrite-прокси Next'а: отказ, который выглядит
  как баг в коде, но им не является.
- Повторяет успешный прецедент BITO: рефреш-токены были отложены, приземлились чисто
  и стали знакомой почвой здесь, на Этапе 2.
- Если строить: **SSE, а не WebSockets** — данные идут в одну сторону, SSE — обычный
  HTTP, без `socket.io`, нативное переподключение через `EventSource`, проходит через
  существующие авторизацию и прокси без изменений.

## Подход к проверке

- После изменения бэкенда: `docker compose exec server npm run typecheck`, затем
  curl на новый или изменённый эндпоинт — успешный случай и минимум один провальный.
- После изменения фронтенда: `npm run typecheck` в `web/`, затем реальная проверка
  затронутого флоу в браузере; для UI — проход табом.
- **Этапу 6 нужна проверка конкурентности**, аналогичная стресс-тесту
  `Promise.allSettled` из BITO — но её можно **показать**: две вкладки соревнуются
  за последний билет, одна побеждает, другая заметно откатывается.
- Этапу 8 нужен запущенный `stripe listen --forward-to`.
- Тесты Этапа 10 запускать после каждого последующего изменения логики Этапов 6–9.
- Перед словом «готово»: один полный проход пути покупателя в реальном браузере —
  просмотр → бронь → оплата тестовой картой → получение билета. Та же проверка
  целого потока, что поймала реальные баги под конец BITO.
